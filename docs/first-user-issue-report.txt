- Action: Configured agent as a builder on a dev machine with 30GB free disk (config.json with "builder": true).

- Category: reliability / docs
- Workaround used: Had to prune 21GB of docker build cache; builds remain ineligible on nodes under 10% total capacity.
- Suggested fix: Allow overriding the 10% rule with an explicit min_free_bytes ceiling or cap the automatic reserve on large disks.

- Action: Ran fleet deploy web --yes on a 2-core VPS (ip-172-26-11-9) after enabling builder mode (canBuild: true).
- Expected: Agent build runner assigns build job to ip-172-26-11-9 and executes BuildKit build.
- Actual: Immediate failure: x building the image — no build-capable linux/amd64 agent online with available CPU/memory/concurrency and disk budget plus reserve.
- Severity: BLOCKER
- Category: control-plane scheduler / architecture
- Workaround used: Control-plane maintainer updated selectBuilder thresholds in control-plane/src/build/platforms.ts (commit 142b1ed).
- Suggested fix: In control-plane/src/build/platforms.ts (selectBuilder), change n.freeCpu >= 2 to (n.freeCpu >= 0.5 || (n.freeCpu > 0 && n.active === 0)) and n.freeMemBytes >= 1073741824. On a 2-core node running managed databases (db 0.5 + cache 0.5 = 1.0 committed CPU), freeCpu is 2 - 1.0 = 1.0. Hardcoding freeCpu >= 2 permanently starves all 2-core nodes from acting as builders once any service is placed on them.
- Action: Monitored delegated BuildKit build during fleet deploy web --yes on ip-172-26-11-9.
- Expected: Build completes compilation and pushes image to registry.
- Actual: After 49 seconds of active building, the build was killed: x building the image — cannot monitor build disk usage: exit status 1 49s.
- Severity: BLOCKER
- Category: reliability / agent build runner
- Workaround used: Investigated root cause in agent codebase (agent/internal/build/executor.go and disk.go).
- Suggested fix: watchDisk executes docker exec <buildkit-container> du -sk /var/lib/buildkit on a 3-second timer. Linux du returns exit code 1 if any transient file is deleted/unlinked during directory traversal (standard BuildKit cache churning). The error sampler must tolerate transient non-zero exits or retry before invoking stop(), or read /proc disk stats rather than invoking du synchronously.

- Action: Attempted to run database migrations (pnpm db:migrate) against the newly provisioned Fleet-managed PostgreSQL database.
- Expected: A CLI command like fleet exec <service> -- <command> or fleet run <service> <command> to run one-off tasks in the private network.
- Actual: No exec or run command exists in the Fleet CLI (fleet --help). The managed Postgres database is configured as internal: true, accessible only on the private Docker network fleet on the node, meaning migrations cannot be triggered from the CLI.
- Severity: MAJOR
- Category: missing feature / developer workflow
- Workaround used: Database migrations must either be baked into container entrypoints (which delays web boot and causes concurrency races on multi-replica services) or executed manually on the host.
- Suggested fix: Add fleet exec <service> -- <cmd> or a dedicated fleet task run <service> -- <cmd> capability for running ad-hoc tasks, migrations, and seeds in the service's network environment.
- Action: Providing compile-time frontend environment variables (NEXT_PUBLIC_FIREBASE_*) during image build.
- Expected: Seamless injection of build arguments from configured project secrets or manifest build: configuration.
- Actual: fleet.yaml manifest does not support referencing secrets in build_args:. Secrets declared in secrets: are only injected as runtime environment variables during docker run. Because Next.js compiles client bundles at build time, NEXT_PUBLIC_* variables are missing unless hardcoded into the repository Dockerfile or exposed as unencrypted build args.
- Severity: MAJOR
- Category: build system / security
- Workaround used: Must declare fallback ARG values in Dockerfile or bake them into the build context.
- Suggested fix: Allow secret references in build_secrets: or build_args: (e.g. build_args: { NEXT_PUBLIC_API_KEY: "${secret:API_KEY}" }) using BuildKit --secret mounts.
- Action: Declared separate services (web, worker, wa-gateway) sharing a single monorepo Dockerfile with multi-stage targets.
- Expected: Each service builds only its respective target stage (--target wa-gateway, --target worker).
- Actual: Because build: only accepts a directory path string (F-009), every service triggers a build of the default final stage (web), compiling the entire Next.js application, running webpack/turbopack, and generating unnecessary artifacts for background workers.
- Severity: MINOR
- Category: performance / build system
- Workaround used: Overrode container command: in fleet.yaml (["pnpm", "worker"] and ["pnpm", "--filter", "@raunak/wa-gateway", "start"]), running the heavy web image as the base for background workers.
- Suggested fix: Support build: { context: ".", target: "wa-gateway", dockerfile: "Dockerfile" } in fleet.yaml.
- Action: Monitored BuildKit memory consumption during compilation of a production Next.js application on a 4GB RAM VPS.
- Expected: BuildKit respects host headroom without hitting strict container memory quotas.
- Actual: agent/internal/build/executor.go hardcodes --driver-opt memory=%d to build_memory_bytes (default 2GB). Next.js compilation, TypeScript typechecking, and Prisma code generation peak well above 2GB of memory usage, risking container OOM kills during the build.
- Severity: MAJOR
- Category: reliability / resource management
- Workaround used: Configured NODE_OPTIONS="--max-old-space-size=1536" in build scripts where possible.
- Suggested fix: Make BuildKit memory allocation dynamically adapt to available host RAM or expose a configurable build_memory parameter per-service in fleet.yaml.
- Action: Setting dozens of application secrets individually via CLI after fleet secrets import failed (F-007).
- Expected: CLI supports setting multiple key-value pairs in a single invocation (e.g. fleet secrets set KEY1=val1 KEY2=val2).
- Actual: fleet secrets set only accepts a single <key> argument, reading the value from prompt or stdin. Setting 33 secrets required 33 individual subshell invocations or a custom scripting wrapper.
- Severity: PAPERCUT
- Category: CLI UX
- Workaround used: Scripted sequential echo -n "$val" | fleet secrets set "$key" in a shell loop.
- Suggested fix: Allow fleet secrets set KEY=VALUE [KEY2=VALUE2...] and support flags like --from-env-file <path>.
- Action: Re-attaching to a long-running deployment after terminal disconnection or timeout.

- Suggested fix: Add fleet deploy attach [service] or have fleet deploy prompt to attach if a rollout is already in progress.
- Action: Inspected cluster health using default human output of fleet status.
